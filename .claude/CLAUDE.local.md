## ワークフローのオーケストレーション

### 注意
* ユーザとのコミュニケーションは日本語で行うこと。
* ユーザからの指示はその視点を含めてissueにて管理すること。

### 1. 計画モードをデフォルトに

* 些細ではないすべてのタスク（3ステップ以上、またはアーキテクチャの決定を伴うもの）では計画モードに入ること。
* 何か問題が起きたら、すぐに停止して再計画すること。無理に押し進めない。
* 構築作業だけでなく、検証のステップにも計画モードを使用すること。
* 曖昧さを減らすため、事前に詳細な仕様を書くこと。

### 2. サブエージェント戦略

* メインのコンテキストウィンドウ（記憶領域）をすっきり保つため、サブエージェントを惜しみなく使用すること。
* 調査、探索、並列分析はサブエージェントに任せる（オフロードする）こと。
* 並列実装可能な実装はサブエージェントに任せること。
* 複雑な問題には、サブエージェントを通じてより多くの計算リソースを投入すること。
* 集中して実行するため、1つのサブエージェントにつき1つのアプローチを割り当てること。

### 3. 自己改善ループ

* ユーザーから修正を受けた後は**必ず**、そのパターンを `tasks/lessons.md` に更新すること。
* 今後の制作開発でも有効だと思う場合は記録すること。
* 同じ間違いを防ぐための自分用ルールを書くこと。
* ミス率が下がるまで、これらの教訓を徹底的に繰り返すこと。
* セッションの開始時に、関連するプロジェクトの教訓を見直すこと。

### 4. 完了前の検証

* 動作を証明せずにタスクを完了（done）とマークしないこと。
* 関連する場合は、mainブランチと自分の変更後の挙動の差分（Diff）を確認すること。
* 「これはスタッフエンジニア（上級エンジニア）が承認するレベルか？」と自問すること。
* テストを実行し、ログを確認し、正確性を証明すること。

### 5. エレガントさの追求（バランス良く）

* 些細ではない変更の場合、立ち止まって「もっとエレガントな方法はないか？」と自問すること。
* 修正が場当たり的（ハッキー）だと感じたら、「今の知識をすべて使って、エレガントな解決策を実装する」こと。
* 単純で明らかな修正の場合はスキップすること。過剰なエンジニアリング（やりすぎ）は避ける。
* 提示する前に、自分の仕事に疑いを持つ（粗探しをする）こと。

### 6. 自律的なバグ修正

* バグ報告を受けたら、とにかく修正すること。手取り足取りの指示を求めない。
* ログ、エラー、失敗しているテストに狙いを定め、それらを解決すること。
* ユーザーにコンテキストスイッチ（状況の把握し直し）を一切させないこと。
* 指示されなくても、失敗しているCI（継続的インテグレーション）テストを修正しに行くこと。
* 手元にある情報で解決できない場合は一次情報は何かどこにあるかから突き止めて情報を集めること。

## タスク管理

1. **まず計画する:** `tasks/todo.md` にチェック可能な項目をまとめた計画を書く。
2. **計画を検証する:** 実装を始める前に確認を入れる。
3. **進捗を追跡する:** 進めながら項目を完了とマークしていく。
4. **変更を説明する:** 各ステップで概要レベルの要約を行う。
5. **結果を文書化する:** `tasks/todo.md` にレビューのセクションを追加する。
6. **教訓を記録する:** 修正作業の後に `tasks/lessons.md` を更新する。

## コア原則

* **シンプルさ第一:** すべての変更をできる限りシンプルにする。影響を与えるコードを最小限にする。
* **怠けない:** 根本原因を見つける。一時しのぎの修正はしない。シニア開発者の基準で取り組むこと。
* **影響を最小限に:** 必要な部分にのみ手を入れること。新たなバグの混入を避ける。
*(※画像では `Minimat Impact` となっていますが、文脈から `Minimal` と解釈して訳しました。また `Bug Fizing` も `Fixing` と解釈しています)*

## ページ別コンポーネント化ワークフロー（スノーボール方式）

### 概要
全ページの全セクションを Components フレーム内の reusable コンポーネントとして管理し、各ページからは ref で参照する。左のページから順に進めることで、右のページほど新規コンポーネントが減る（スノーボール効果）。

### ページ処理順序（左→右）— 全ページ完了
1. **トップページ** — 全コンポーネント化済み ✓
2. **客室ページ** — 全コンポーネント化済み ✓
3. **温泉ページ** — 全コンポーネント化済み ✓
4. **お料理ページ** — 全コンポーネント化済み ✓
5. **過ごし方ページ** — 全コンポーネント化済み ✓
6. **アクセスページ** — 全コンポーネント化済み ✓
7. **予約ページ** — 全コンポーネント化済み ✓
8. **お問い合わせページ** — 全コンポーネント化済み ✓

### 各ページの処理手順
1. **共通コンポーネント確認**: Header, Breadcrumb, CTA, Footer 等が既にコンポーネント化済みなら ref で配置（重複作成しない）
2. **固有セクションの棚卸し**: そのページ固有のセクションを特定
3. **3ビューポート分コンポーネント化**: PC/Tablet/Mobile の固有セクションを Components フレームに I() で reusable 作成
4. **ページに ref 配置**: 元のインラインセクションを D() → ref で置換
5. **スクリーンショット検証**: 全ビューポートで get_screenshot 確認

### 重複チェックルール
* 前ページまでで同じセクション構造のコンポーネントが存在する場合は、ref で再利用する
* CTA/Footer/Header は全ページ共通 → 必ず既存コンポーネントの ref を使用
* Breadcrumb/Page Hero も共通パーツ → ref + descendants でテキスト差し替え

### Components フレーム構造
```
Components (cRCB2)
├── Parts (fUIrU, width: 400)
├── PC (RlMpE, width: 1440)
├── Tablet (IQzum, width: 768)
└── Mobile (DwO7w, width: 375)
```

## デザイン・実装ルール（セッション分析 2026-02-24 より）

### デザイン変更順序
* .pen デザインファイルが Single Source of Truth (SSOT)。
* コード実装は .pen デザイン完成後に行う。.pen 未確定の状態でコード先行しない。
* ユーザー承認なしにデザイン判断（フォントサイズ・色・レイアウト変更等）をしない。

### コンテキスト圧縮対策
* 承認済みデザイン決定は GitHub Issue にコメントで記録し、コンテキスト圧縮後も参照可能にする。
* 長時間セッションでは、重要な承認事項を Memory MCP にも保存する。

### Pencil MCP 変更後の検証
* `batch_design` 実行後は必ず `get_screenshot` で目視確認する。「変更なし」と判断してスキップしない。
* R() (Replace) 操作実行前に、対象ノードが他スクリーンから参照されていないか確認する。
